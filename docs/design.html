Groundtruth Pipeline

Groundtruth is an AI code reviewer that only posts a finding when it can prove it. Written in Python, MIT-licensed.

Most AI reviewers aim for coverage and comment on everything. This one aims for precision, because a wrong comment costs more trust than a missed bug. Context is parsed, not retrieved, and nothing posts without surviving verification.

The handoff, stage by stage

The seven stages

01 Trigger

A pull request event starts the run. The CI job checks out the repository with full history and calls one command, groundtruth review.

Why CI: the platform's own runner is already the queue and the compute. Nothing has to be hosted, so installing the tool is one workflow file and one secret.

02 Collect the change

Git provides the diff and the full text of each changed file at both the base and the head commit.

Why both versions: the diff alone shows changed lines without the code around them, and comparing the two versions is what reveals that a function's signature changed.

03 Build context

This stage decides what the model is allowed to see. It makes no AI calls.

  • Tree-sitter parses each changed file into an AST, so a changed line becomes the whole function that contains it.
  • ripgrep searches the repository for callers of each changed function, with a plain Python walk as a fallback when ripgrep is missing.
  • If a function's signature changed, its callers become must-include and can never be dropped.
  • Everything is packed into a token budget. Optional blocks shrink to their signature line before being dropped, and every cut is reported.

Why an AST instead of a vector database: parsing is exact and repeatable. Similarity search returns code that merely looks related, and a wrong snippet produces a confident, wrong finding. This way, context is always real code that provably surrounds the change.

04 Propose findings

The context bundle from stage 3 is built once for the whole pull request. The reviewer then makes one call per changed file: each call carries that same bundle as reference, plus one file's diff as the code actually under review. Each finding must quote the exact line it is about. LiteLLM is used as a library, so the model is one line of config — Claude, OpenAI, Azure, Bedrock or a local Ollama model — and the key comes from an environment variable.

Why the target is one file, not the whole diff: a single pass over a large diff reports the few most obvious issues and stops looking. The reference material is not what causes that, so the bundle stays whole; only the code under review is kept small, which is why the fifteenth file gets the same attention as the first.

Why the quote: it is the evidence the next stage checks. A model can claim anything, but it cannot copy a line that was never written.

05 Verify: the quality gate

Nothing reaches the pull request without clearing five checks, ordered cheapest first so paid calls are only spent on candidates that could survive.

CheckHow it worksWhy
Quote exists Whitespace-insensitive text match against the diff and context Removes invented code before anything else runs
Line is in the diff The reported line must fall inside a changed hunk of that file A quote can be real while the line reported with it is wrong, and no comment can be placed on a line the diff does not contain
Not a duplicate SHA-1 fingerprint of file, surrounding code and category — never the model's wording A reworded finding on untouched code keeps the same ID, so re-runs don't repeat comments
Skeptic pass A second LLM call judges whether the finding is real and worth fixing; its confidence is multiplied with the first model's Averaging lets a confident wrong answer outvote a doubtful right one. Multiplying makes doubt contagious
Rank and cap Sorted by severity weight × confidence, trimmed to a maximum Keeps reviews short, so the comments people do see are the ones worth reading

Every rejected finding records which check dropped it and why, which is what makes review quality measurable later.

06 Summarize

A cheap call turns the verified findings into the text of one summary comment. Grouping findings that share a cause — three instances of the same missing null check — reads faster than three bullets that look unrelated.

The guard: this is the only text on the pull request the gate never checked itself, so the summarizer may only group and rephrase findings that already passed — never add a claim. A summary naming a file or line outside the verified set is discarded, and any error falls back to a plain formatted list. A bad call costs wording, never the review.

The call belongs to the core, not to a platform adapter, and its text travels as a summary field in the same JSON. Every adapter gets it without making a model call of its own.

07 Publish

One summary comment is created or updated, plus one comment on the code for each finding.

Why a separate adapter: it depends only on the JSON the command prints, not on the tool's internals. Supporting GitLab or Bitbucket is then glue code for a different API, not a redesign.

A worked example

One pull request, traced through every stage. calculate_discount gains a required promos argument. checkout.py is not part of the pull request and still calls it with one argument — the break a diff-only review cannot see.

Stages 1–2 · the change that arrives

diff --git a/invoice.py b/invoice.py
@@ -1,6 +1,7 @@
-def calculate_discount(price):
-    return price * 0.9
+def calculate_discount(price, promos):
+    rate = 1 - sum(p.rate for p in promos)
+    return price * rate


-def invoice_total(price):
-    return calculate_discount(price)
+def invoice_total(price, promos):
+    return calculate_discount(price, promos)

Parsed into one file, added lines 1, 2, 3, 6 and 7, and a single hunk spanning lines 1–7. Those spans are what stage 5 later checks a reported line against.

Stage 3 · the context assembled

invoice.py#L1-3 (changed: signature changed)
    def calculate_discount(price, promos):
        rate = 1 - sum(p.rate for p in promos)
        return price * rate

invoice.py#L6-7 (changed: signature changed)
    def invoice_total(price, promos):
        return calculate_discount(price, promos)

checkout.py#L4-5 (caller of calculate_discount, signature changed)
    def checkout(price):
        return calculate_discount(price)          <-- still the old call

3 blocks, 68 tokens, nothing cut

No model has been called yet. The signature changed between base and head, so every caller of calculate_discount is promoted to must-include — which is how the untouched checkout.py reaches the reviewer at all.

Stage 4 · what the model proposes

{"findings": [
  {"file": "invoice.py", "line": 1, "category": "correctness", "severity": "high",
   "confidence": 0.9,
   "title": "New promos argument is required, but checkout.py still calls calculate_discount(price)",
   "quoted_code": "def calculate_discount(price, promos):"},

  {"file": "invoice.py", "line": 2, "category": "correctness", "severity": "medium",
   "confidence": 0.8,
   "title": "Empty promos list is not handled",
   "quoted_code": "rate = 1 - sum(p.rate for p in promos or [])"}
]}

Note where the first finding sits: on the changed line in invoice.py, naming checkout.py in its text. A finding must live inside the diff, so a break in an untouched file is reported against the change that caused it.

Stage 5 · what the gate does with them

candidate 1  quote found in the diff ....... pass
             line 1 inside hunk 1-7 ......... pass
             fingerprint 596cc47b1d8b ....... new
             skeptic: real, actionable, 0.9 .. 0.9 × 0.9 = 0.81
             → posted

candidate 2  quote found in the diff ....... FAIL
             → dropped at the quote check, no model call spent

The second quote looks plausible and appears nowhere in the diff: the real line has no or []. It is rejected before the skeptic pass, so the fabrication costs nothing.

Stages 6–7 · what lands on the pull request

## Groundtruth review

**1 verified finding**, grouped by file.

#### `invoice.py`

| Severity | Line | Finding                                       | Confidence |
| ---      | ---  | ---                                           | ---        |
| **HIGH** | 1    | New promos argument is required, but          | 0.81       |
|          |      | checkout.py still calls calculate_discount()  |            |

<sub>1 candidate finding(s) did not survive verification.
Reviewed with `anthropic/claude-sonnet-5` · estimated $0.0032.</sub>

The summary call is handed the one verified finding and returns a sentence for the top of the comment — here, “A required argument was added to calculate_discount without updating its caller.” It names only invoice.py, a file in the verified set, so it passes the grounding check; a sentence naming anything else would be discarded and the plain list posted instead. Alongside the comment, one inline comment lands on invoice.py:1 with the severity, category, confidence and quoted line.

Which model does what

Three stages call a model, and they do not need the same one. The model is a config line, so the tier is a deployment choice rather than a code change.

StageTierWhy
4. Propose Stronger Reads a whole file's diff against the context bundle. The ceiling on review quality is set here
5. Verify Cheap One bounded question about one finding and its evidence, on a short prompt
6. Summarize Cheap Rephrasing text that is already verified, once per pull request

Why the reasoning gets the stronger tier: a finding that was never proposed cannot be recovered downstream, while a finding that was proposed still has to get past the gate. Spend where the reasoning happens, not where the checking does.

The cheap tier is safe in stage 5 because most of that stage is not a model call at all. The quote match, the location check, the fingerprint and the ranking are ordinary code — exact, free, and unaffected by which model is configured. Only the skeptic's judgement is a call, and its confidence multiplies, so an unsure verdict pulls a finding below the bar rather than waving it through.

What it deliberately does not use

Several obvious pieces are missing on purpose. Each was left out for a reason worth knowing before adding it back.

Not usedUsed insteadReason
Vector database, embeddings, RAG AST parsing plus a caller search Retrieval guesses at relevance; a wrong snippet turns into a confident, wrong finding
A hosted service or shared API key The user's own key from an environment variable No shared bill, no contract, and a local Ollama model costs nothing
Server, queue and database for normal use A stateless CI job One person reviewing their own repository needs a key, not a fleet
Spend governance built into the tool An optional self-hosted LiteLLM proxy, set by one config line Budgets and caps already exist in that open-source proxy; rebuilding them would add no value
Keys in a config file Environment variables only, with the config file refusing to load anything key-shaped A file that could hold a secret is a file someone eventually commits
Averaged confidence scores Multiplied scores A false positive costs more trust than a missed bug, so either model's doubt must be able to block a finding

One more boundary holds the design together: the context and verification packages never import platform code. They take a diff and a repository path, and return findings. That is what makes “any platform, any model” true rather than a slogan.
